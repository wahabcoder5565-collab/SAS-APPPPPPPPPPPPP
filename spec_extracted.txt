Refinery Air-PermitChange Deployment Agent
Product & Build Specification


One-sentence product definition
An AI agent for refinery environmental teams that compares revised air permits with the current permit, maps changed obligations to facility-specific assets and controls, and produces a human-reviewed implementation plan with traceable evidence.

1. Mission
Build a convincing vertical AI implementation that demonstrates how an agent can turn a dense regulatory change into concrete, facility-specific operational work. The prototype should feel like software built for one refinery, not a generic compliance chatbot.

The core transformation
Before: a 1,000+ page revised permit and a team manually hunting for implications.  After: a ranked change register showing exactly which assets, SOPs, monitoring rules, calculations, forms, owners, and evidence packages are affected.
Success is not “the AI answered a question.”
Success means the system can visibly demonstrate this chain:
Permit change
Affected asset
Affected control
Required action
Evidence
Human approval

Portfolio objective
The finished project should prove competence in document intelligence, RAG, structured data, agentic workflows, graph-style relationships, confidence scoring, human-in-the-loop design, auditability, and AI evaluation.
2. Real-World Rationale
This workflow is grounded in real refinery permitting work. Barr describes supporting Flint Hills Resources’ Pine Bend Refinery with a custom AI-assisted review of a 1,500-page draft air permit. Barr states that a traditional review would have required weeks of manual work by experienced staff. Their workflow performed line-by-line comparison, classified changes, assigned confidence, and supported expert review.
Title V operating permits contain enforceable monitoring, recordkeeping, and reporting obligations. Large refinery enforcement actions also demonstrate that air-compliance failures can carry substantial financial consequences. This prototype is not intended to calculate legal exposure; the point is that the workflow is attached to real operational risk.
Why this is a good AI project
Specific trigger: a new or revised permit arrives.
Specific buyer: environmental / air-quality compliance team.
Specific job: understand changes and implement them correctly.
Facility-specific context: the same permit sentence can affect different assets and controls at different sites.
High auditability requirement: every conclusion should trace back to source text and facility evidence.
Natural human approval point: regulatory judgments and operational changes are never silently auto-approved.

4. Scope
V1 must do
Store two permit versions: current and proposed/reissued.
Extract permit requirements into structured records with source-page citations.
Compare old vs. new requirements using semantic and numeric change detection.
Classify changes by impact and confidence.
Maintain a synthetic facility model: emission units, monitoring points, SOPs, forms, calculations, training documents, and owners.
Map changed requirements to relevant facility entities.
Detect conflicts between new requirements and existing controls.
Generate a proposed implementation plan.
Create review tasks with owners, status, due date, and evidence requirements.
Accept implementation evidence and run an AI evidence-completeness check.
Require explicit human approval before a change is marked closed.
Provide an audit trail showing what the AI read, inferred, proposed, and what the human approved.
V1 explicitly does NOT do
Submit anything to a regulator.
Make final legal or regulatory determinations.
Change PLC, DCS, CEMS, alarm, or plant-control settings.
Connect to a real refinery system.
Predict enforcement penalties.
Replace environmental engineers or legal counsel.
Attempt every type of air permit or every jurisdiction.
Build billing, CRM, multi-tenant SaaS, public sign-up, or subscription management.

7. Agentic Workflow
1.  Ingest. Parse both permit versions and facility documents.
2.  Extract. Convert permit clauses into structured obligations.
3.  Diff. Pair old and new obligations and identify additions, removals, numeric changes, frequency changes, and wording changes.
4.  Prioritize. Score likely operational impact and confidence.
5.  Resolve context. Search the facility model for relevant units, pollutants, monitoring systems, procedures, forms, calculations, and owners.
6.  Propagate. Identify downstream records or controls that appear inconsistent with the revised requirement.
7.  Plan. Generate proposed implementation actions and evidence requirements.
8.  Review. Require a human to approve or correct the interpretation.
9.  Verify. When evidence is submitted, check whether it appears to address the approved action.
10.  Close. Only a human can mark the implementation complete.

Agent rule
The agent may propose, compare, search, link, rank, summarize, and verify evidence. It may not silently make a consequential compliance or operating decision.

Prefer explicit deterministic code for numeric comparisons, units, dates, and status transitions.
11. AI / Retrieval Design
Use the LLM for
Classifying clauses and extracting structured attributes.
Pairing semantically equivalent clauses across versions.
Summarizing substantive wording changes.
Generating candidate facility relationships.
Explaining why a document/control appears affected.
Drafting proposed implementation actions.
Checking whether submitted evidence appears responsive to an action.
Do NOT use the LLM alone for
Numeric delta calculation.
Unit conversion.
Date arithmetic.
Final compliance status.
Final asset/control mapping when confidence is low.
Closing implementation actions.
Retrieval strategy
Use metadata filters first, then semantic retrieval. Example: if a changed requirement mentions NOx and Boiler B-07, filter for documents tagged to B-07 / combustion / NOx before vector similarity. This prevents the system from retrieving a semantically similar but irrelevant SOP from another process unit.
Citation contract

No evidence, no claim
Every material AI finding in the UI should carry either (a) a permit source reference, (b) an internal document reference, or (c) an explicit “inference / needs review” label.

Meaning
System behavior

Strong contextual match but not explicit

A good prototype should visibly admit uncertainty. A wrong but confident compliance mapping is much worse than an honest unresolved item.

16. Definition of Done
The project is done when a reviewer can perform this exact demo:
1.  Open NorthRiver Refining.
2.  Select Current Permit vs. Revised Permit.
3.  Run / view the completed comparison.
4.  See a ranked list of substantive changes.
5.  Open Boiler B-07 NOx change.
6.  Inspect old/new permit citations.
7.  See the linked asset and affected SOP / monitoring control / calculation / training items.
8.  See why each relationship was proposed and its confidence.
9.  Open the generated implementation actions.
10.  Upload or select simulated evidence for one completed action.
11.  See the AI evidence check.
12.  Approve the action as a human reviewer.
13.  Open the audit trail and trace the full path from permit clause to approval.

Hard completion criterion
If the demo still depends on the presenter explaining what the product is supposed to do, it is not finished. The UI must make the permit-change → facility-impact → implementation-evidence chain obvious.

19. Final Instruction to the Builder

Build the workflow, not the buzzwords.
The goal is not to say “I used agents, RAG, vectors, and a knowledge graph.” The goal is to make one realistic permit change travel through a believable refinery model until the reviewer can see exactly what must change, why, and what evidence proves it was handled.
Start with the Boiler B-07 case. Make that single chain excellent. Then generalize. One deep, defensible workflow is more valuable than twenty shallow AI features.
